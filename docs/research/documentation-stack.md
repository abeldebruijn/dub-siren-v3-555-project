# Documentation stack for the Breadboard language

Research date: 2026-08-08

## Revised recommendation

Use **Rspress as a documentation package in the existing monorepo**. Keep the
current Vite application as the playground, but let Rspress own the language
manual, its routes, persistent chapter sidebar, page outline, and keyword
search.

The earlier recommendation—raw MDX inside the Vite application—was appropriate
for one documentation page. It is no longer the best fit now that the desired
experience is a React-docs-style manual with:

- a persistent, grouped sidebar containing every chapter;
- full-text keyword search across headings, prose, syntax, positions, pin names,
  and aliases;
- a page outline for sections within a long chapter;
- interactive React examples embedded in the documentation;
- fully static GitHub Pages deployment.

Rspress provides these as one React-based documentation system. Its default
layout includes navbar, sidebar, and a right-hand outline generated from page
headings. Its sidebar may be declared or generated from `_meta.json`, including
a single global sidebar and collapsible groups
([Rspress introduction](https://www.rspress.dev/guide/start/introduction),
[autogenerated navigation](https://www.rspress.dev/guide/basic/auto-nav-sidebar)).
It also generates a full-text search index during builds, exposes search in its
default theme, and provides hooks for processing keywords or filtering results
([Rspress overview](https://www.rspress.dev/),
[search hooks](https://www.rspress.dev/guide/advanced/custom-search)).

Rspress MDX compiles to React components and can directly render imported TSX
components. It also reuses a project-installed React version, so the existing
Breadboard compiler, renderer, and mini-playground can be shared as workspace
code instead of being adapted into another UI framework
([MDX and React components](https://www.rspress.dev/guide/use-mdx/components)).

Do **not** use `react-docgen` for the manual. It is a low-level analyzer that
extracts React component metadata as JSON; it does not provide a documentation
shell, language-reference structure, or search
([react-docgen overview](https://react-docgen.dev/),
[output model](https://react-docgen.dev/docs/reference/documentation/basic)).
It could document `MiniPlayground` props later, but it cannot document the
Breadboard language.

## Comparison for the revised requirements

| Option | Sidebar and page outline | Static keyword search | Interactive Breadboard examples | Integration cost | Verdict |
| --- | --- | --- | --- | --- | --- |
| **Rspress** | Built-in global/grouped sidebar and heading outline | Built in; generated during the static build | Native React components in MDX; shares compiler and UI code directly | A docs package and build, but little custom docs infrastructure | **Choose** |
| Astro Starlight | Built-in configurable sidebar and page TOC | Built-in Pagefind full-text search | React is supported in MDX, but each editor is a hydrated React island in Astro | Separate Astro app, React integration, hydration choices, and restyling | Strong alternative, but less direct for this React-heavy manual |
| Raw MDX in existing Vite app | Must build and maintain the sidebar, active-heading state, mobile drawer, and outline | Must add a custom content index or Pagefind build; the current client-rendered hash routes are not useful static HTML search documents | Easiest possible component reuse | Initially small, but now requires recreating a docs framework | Second choice only if keeping one app is more important than docs features |
| `react-docgen` | None | None | Not applicable | Wrong abstraction | Reject |

Starlight is the closest alternative. It provides a configurable or
filesystem-generated sidebar and a right-hand table of contents
([configuration reference](https://starlight.astro.build/reference/configuration/),
[sidebar guide](https://starlight.astro.build/guides/sidebar/)). It includes
Pagefind full-text search with no configuration, and Pagefind remains entirely
static with no search server
([Starlight site search](https://starlight.astro.build/guides/site-search/),
[Pagefind overview](https://pagefind.app/)). Starlight can use React components
inside MDX, but this requires Astro's React support and client hydration for
interactive editors
([Starlight components](https://starlight.astro.build/components/using-components/)).
That is a reasonable trade for a mostly static manual, but Rspress is simpler
when nearly every syntax section contains a live React compiler example.

Raw MDX remains technically possible through `@mdx-js/rollup`
([MDX Vite setup](https://mdxjs.com/docs/getting-started/)). Pagefind can index
any static HTML output and provides both a JavaScript API and accessible search
components
([Pagefind setup](https://pagefind.app/docs/),
[component UI](https://pagefind.app/docs/search-ui/)). However, the existing
Vite site is a client-rendered application with hash routes, so producing
separate searchable HTML documents would require prerendering or maintaining a
parallel search index. It would also leave the chapter sidebar, responsive
navigation, active state, keyboard search dialog, and page outline as custom
application code. Those are now core requirements, not incidental styling.

## Proposed documentation information architecture

Use multiple chapter pages in the sidebar, while keeping the complete formal
grammar together on one dedicated page:

1. **Introduction**
   - complete editable program;
   - link to the full playground;
   - installation and configuration placeholders.
2. **Language**
   - **Complete grammar** — every formal production on one page;
   - breadboard declaration;
   - components and placement;
   - wires.
3. **Reference**
   - breadboard positions;
   - position shortcuts and deterministic expansion;
   - component pins;
   - pin aliases;
   - diagnostics.
4. **Examples**
   - two connected components;
   - common wire connections.

The left sidebar should show those chapters and pages at all times. The
right-hand outline should show headings on the current page. On the complete
grammar page, the outline therefore becomes the index of every grammar item.
Search should open from the top bar and by keyboard shortcut, returning the
matching section rather than only the containing chapter.

## Content and search rules

Rspress warns that TSX/HTML-heavy document content is harder to extract for
local search, and recommends keeping document content in MDX while putting
interactive behavior in TSX
([Rspress MDX guidance](https://www.rspress.dev/guide/use-mdx/components)). Follow
that separation deliberately:

- Put every canonical term, coordinate form, shortcut, pin name, and alias in
  MDX prose, headings, tables, or static code blocks.
- Put the editable compiler, SVG preview, and diagnostics panel in a reusable
  `BreadboardExample` React component.
- Do not rely on initial editor text as the only searchable occurrence of a
  syntax form.
- Give every grammar item and reference entry a stable heading anchor, so a
  search result can open the exact section.
- Keep aliases beside their primary pin names in a static reference table even
  when the same data also drives an interactive pin diagram.

## Grammar source of truth

The formal grammar should still come from the executable Chevrotain parser, not
from a hand-maintained duplicate. The repository already generates a railroad
document and tests its freshness
([grammar generator](../../packages/breadboard/scripts/generate-grammar.mjs)).
Chevrotain supports generating self-contained syntax-diagram HTML for docs
([Chevrotain syntax diagrams](https://chevrotain.io/docs/guide/generating_syntax_diagrams.html)).

Use the generated output on the **Complete grammar** page, then follow each
production with human-written MDX explanation and a compact editable example.
This preserves one authoritative grammar while making every item searchable and
teachable.

## Deployment shape

Add Rspress as a workspace package and build it under a stable documentation
base path such as `/pico-dub-siren/breadboard/docs/`. Rspress emits static HTML,
supports a project `base`, and documents a GitHub Pages Actions deployment
([Rspress deployment](https://www.rspress.dev/guide/basic/deploy),
[static generation](https://www.rspress.dev/guide/basic/ssg)). The final Pages
artifact can contain both:

- the existing Vite playground/application; and
- the Rspress documentation output under `/docs/`.

This keeps one GitHub Pages site while allowing the application and manual to
use the tools best suited to each job.
